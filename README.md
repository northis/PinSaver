# PinSaver — локальный архив пинов Pinterest

PinSaver — это self-hosted архив пинов Pinterest в исходном качестве: сервер на FastAPI + SQLite
с веб-интерфейсом (мозаика, бесконечная прокрутка, полноэкранная карусель, удаление) и расширение
Chrome, которое сохраняет пины прямо со страниц Pinterest, помечает уже сохранённое в избранном
и умеет заливать архив обратно в профиль.

Версия и коммит сборки всегда видны: в шапке сайта и на странице настроек расширения — `vX.Y.Z`
ведёт на тег релиза, короткий хеш — на коммит в GitHub.

## Возможности

- **Веб-интерфейс** — мозаика с бесконечной прокруткой, полноэкранная карусель, сортировки
  (новые, старые, по рейтингу, случайно) и фильтр удалённых пинов.
- **Расширение Chrome** — кнопка «Save» на странице пина сохраняет оригинал изображения в архив.
- **Метки в избранном** — на страницах профиля каждый пин получает значок: `✓` (уже в архиве) или
  `↓` (можно сохранить одним кликом).
- **Синхронизация в Pinterest** — плавающая кнопка «🔄 Sync to Pinterest» заливает архив обратно
  в профиль (Quick Saves).
- **Рейтинг** — повторные сохранения одного и того же изображения увеличивают счётчик: видно, что
  нравится больше.
- **Проверка удалённых пинов** — headless Chromium проходит по ссылкам и помечает то, что Pinterest
  больше не отдаёт.
- **Бэкапы** — инкрементальные zip-архивы базы и новых оригиналов.
- **Страница обслуживания** — на отдельном локальном порту: скачать полный архив (база + все
  картинки), запустить инкрементальный бэкап и скачать любой из готовых.

## Быстрый старт

### 1. Клонировать и поставить зависимости

```bash
git clone https://github.com/northis/PinSaver.git
cd PinSaver
python -m pip install -r src/requirements.txt -r src/requirements-tools.txt
```

Нужен Python 3.10+. `requirements.txt` — то, что нужно серверу (его же ставит контейнер),
`requirements-tools.txt` — хостовые скрипты и инструменты: `updateDelete.py` требует Playwright с
браузером, `importer.py` — BeautifulSoup, `tools/` — Pillow.

Тесты идут офлайн и не трогают архив:

```bash
python -m pip install -r src/requirements-dev.txt
python -m pytest -q
```

### 2. Настроить окружение

```bash
cp .env.example .env
```

```env
HOST=0.0.0.0
PORT=8000
```

### 3. Создать базу

```bash
python src/models.py
```

Появятся `pinterest_archive.db` и папка `originals/` для картинок.

### 4. Запустить сервер

```bash
python src/server.py
```

Сайт — `http://localhost:8000`, версия и коммит — в шапке страницы.

### 5. Поставить расширение

1. Открой `chrome://extensions/`, включи «Режим разработчика».
2. «Загрузить распакованное расширение» → папка `extension/`.
3. Открой настройки расширения (клик по иконке в панели или «Подробнее» → «Параметры расширения»)
   и проверь адрес сервера — по умолчанию `http://localhost:8000`.

Адрес — единственное, что настраивается. На машине с сервером оставляй `http://localhost:8000`:
это обязательное право расширения, Chrome ничего не спрашивает. На второй машине, где сервера нет,
впиши публичный адрес архива (`https://pinsaver.<домен>`) и нажми `Save Settings` — Chrome покажет
промпт на доступ к сайту, и его надо разрешить. Без разрешения расширение не сходит на сервер, а
скажет «выдай доступ».

## Запуск в Docker

```bash
docker compose up -d --build
```

В образ идёт только рантайм (`src/requirements.txt`), а архив — база, `originals/` и `backups/` —
монтируется с хоста как `/data`, поэтому пересборка и удаление контейнера данные не трогают.
Порт публикуется дважды, и это осознанно: `127.0.0.1:8000` нужен расширению (обязательные права
манифеста — только pinterest и localhost), а `${PINSAVER_BIND_ADDR}:8000` — Traefik'у на хосте
sitehub, куда тот ходит по VPN. Публичного адреса в обязательных правах нет: его выдаёт Chrome в
рантайме, когда владелец вводит адрес в настройках, — в репозитории адрес не хранится. Настройки —
в `.env` (см. `.env.example`).

Третий порт — страница обслуживания: `127.0.0.1:8001` по умолчанию. Она отдаёт весь архив, поэтому
публикуется только на локальных адресах (`PINSAVER_ADMIN_BIND_ADDR`), а не на VPN-адресе сайта.

```bash
curl http://127.0.0.1:8000/api/version   # версия и коммит, вшитые в образ
docker compose ps                        # healthy означает, что healthcheck прошёл
docker compose logs -f pinsaver          # логи: json-file, 10 МБ x 3
docker compose down                      # остановить; данные остаются на месте
```

Версия и коммит попадают в образ двумя путями: `update.ps1` передаёт их build-аргументами, а при
обычной сборке коммит читается из `.git/HEAD` и `refs/`, которые `.dockerignore` оставляет в образе
(самого git в контейнере нет). Поэтому бейдж на сайте и `/api/version` показывают то, что реально
собрано, а не то, что лежит в рабочей копии.

## Публикация в интернете: sitehub + Cloudflare Access

Сайт живёт на этом ПК, а наружу его отдаёт [sitehub](https://github.com/northis/sitehub) — Traefik на
Ubuntu-сервере с wildcard-сертификатом, который ходит к нам по SoftEther VPN на
`${PINSAVER_BIND_ADDR}:8000`. Порядок:

1. Контейнер поднят на ПК (`docker compose up -d`), адрес в VPN — тот же, что у duosave
   (`10.77.77.21`).
2. В sitehub в `traefik/dynamic/vpn-sites.yml` вставляется фрагмент `deploy/sitehub/pinsaver.yml`
   (заменить домен и адрес VPN). Он добавляет **два** роутера: основной — за проверкой
   `cf-access-verify@file`, и публичный для трёх путей: `/manifest.webmanifest`,
   `/static/favicon.svg` и `/static/icons/*`. Без публичного роутера Google не соберёт WebAPK,
   и PinSaver не появится в системном «Поделиться».
3. В Cloudflare Access этим же трём путям нужна политика **Bypass** (Include = Everyone): политика на
   крае и проверка на входе sitehub — два независимых слоя, нужны оба.
4. Проверка:

```bash
curl -s -o /dev/null -w '%{http_code}\n' https://pinsaver.<домен>/manifest.webmanifest          # 200 без сессии
curl -s -o /dev/null -w '%{http_code}\n' https://pinsaver.<домен>/static/favicon.svg            # 200 без сессии
curl -s -o /dev/null -w '%{http_code}\n' https://pinsaver.<домен>/static/icons/icon-192.png     # 200 без сессии
```

Установленное ранее приложение подтянет новый манифест при следующем запуске; если иконка на домашнем
экране осталась прежней, удалите приложение и поставьте заново — прежние пути (`/static/manifest.json`
и `/static/icon-*.png`) в 2.2.0 убраны, а новые должны быть открыты в обоих слоях.

Сайт без сессии Access открываться не должен: внутри приложения авторизации нет, Access — единственный
вход снаружи. Порт `8000` в интернет не публикуется (в `ports` только `127.0.0.1` и VPN-адрес), а
изменяющие запросы требуют заголовок `X-PinSaver-Request: 1` и отвергают чужие источники.

## Обновление

```powershell
powershell -ExecutionPolicy Bypass -File deploy\windows\update.ps1
powershell -ExecutionPolicy Bypass -File deploy\windows\update.ps1 -Rollback
```

Скрипт делает `git fetch`, fast-forward, читает версию в целевом коммите, собирает образ из **чистого
worktree** этого коммита (незакоммиченные правки в образ не попадают), поднимает контейнер и ждёт,
пока `/api/version` не покажет новый коммит; если не дождался — возвращает прошлый образ и падает с
ошибкой. Если контейнер уже на нужном коммите, скрипт просто выходит (`-Force` — пересобрать).

Если git-команда падает, скрипт печатает её собственный текст, а не только код возврата: без этого
любой сбой выглядит как «failed with exit code 1». Сам `git fetch` повторяется трижды с паузой —
параллельный git-процесс (обычно только что запущенный push или git-интеграция редактора) может
держать блокировку ссылки секунду и уронить fetch с кодом 1. Если сети нет вовсе, обновление можно
поднять из уже выкачанного коммита: `-SkipFetch`.

Руками то же самое: `git pull` и `docker compose up -d --build`.

После обновления сервера **перезагрузите расширение** в `chrome://extensions`: в нём появился заголовок
гарда, и старое расширение получит `403` с текстом «reload the extension».

У уже настроенного расширения с публичным адресом обновление требует одного действия: открой
настройки и нажми `Save Settings` (или `Grant access`) — Chrome покажет промпт на доступ к адресу
архива. Пока право не выдано, запросы отвечают `NO_PERMISSION` («выдай доступ»), а не уходят на
сервер.

## Расширение Chrome

### Сохранение пина

На любой странице пина появляется кнопка «Save» — она скачивает оригинал изображения в `originals/`
и добавляет запись в базу. Повторное сохранение того же изображения не создаёт дубликат, а поднимает
рейтинг.

### Метки в избранном

На странице профиля (свои или чужие сохранённые пины) каждый пин получает значок в левом верхнем углу:

- **✓ (зелёный)** — пин уже в архиве;
- **↓ (серый)** — нажми, чтобы сохранить.

### Синхронизация обратно в Pinterest

На любой странице Pinterest в правом нижнем углу появляется кнопка «🔄 Sync to Pinterest»: она
по очереди отправляет не удалённые пины из архива в твой профиль. Нужен активный вход в Pinterest —
расширение использует cookies браузера.

### Настройки

На странице настроек — адрес сервера, строка состояния доступа (`Access to server: granted` или
`Access to server: not granted` и кнопка `Grant access`), кнопка `Save Settings`, ссылка на архив,
иконка расширения и бейдж сборки: версия расширения (из манифеста, ведёт на тег релиза) и короткий
хеш коммита (приходит с сервера, ведёт на коммит в GitHub). Если сервер недоступен, вместо хеша
показывается «server unavailable».

`Save Settings` и `Grant access` делают одно и то же: просят у Chrome доступ к введённому адресу
(промпт показывается только по клику), сохраняют адрес и проверяют соединение. Два разных текста
об ошибке означают разное: `Cloudflare Access needs a sign-in — open the archive in this browser
first.` — право есть, но браузер не залогинен в Access, открой архив в этом браузере; `Access to
this server is not granted — press Save to allow it.` — права нет, нажми `Save Settings` и разреши
промпт.

### Проверка вручную

Автотестов на JS в репозитории нет, поэтому расширение проверяется руками — в Chrome с
перезагруженным расширением:

1. **Машина без сервера**: впиши публичный адрес, нажми `Save Settings`, разреши промпт Chrome —
   тест соединения покажет версию и коммит сервера.
2. Сохрани пин со страницы Pinterest и найди его в архиве.
3. Выйди из Cloudflare Access, нажми «Save to archive» — должно появиться «нужен вход», а не ошибка
   разбора JSON.
4. Отзови право в `chrome://extensions`, нажми «Save to archive» — должно появиться «выдай доступ».
5. **Машина с сервером**: `http://localhost:8000` работает без промптов, как раньше.
6. Смени адрес на другой origin — право просится заново, старое снимается.

## Сохранение с телефона (share)

На Android пин можно сохранить прямо из приложения Pinterest: «Поделиться» → PinSaver. Сервер сам
откроет страницу пина анонимно, найдёт картинку и положит её в архив — cookie Pinterest для этого не
нужны, приватных пинов в архиве нет.

Что нужно:

1. сайт опубликован (см. «Публикация в интернете»): share target работает только у установленного
   приложения, а установка требует HTTPS и service worker;
2. на телефоне откройте сайт в Chrome и установите его (⋮ → «Установить приложение»);
3. после обновления сайта до версии с share-целью приложение может держать старый манифест —
   **удалите и установите его заново**, иначе шара ответит «The app has not updated»;
4. сделайте сессию Cloudflare Access подлиннее: если она истечёт, шара упрётся в страницу входа.

Как это работает: системное «Поделиться» шлёт `POST /share`; service worker (`/sw.js`) перехватывает
ровно эту навигацию, читает три поля share-цели (`url`, `text`, `title`) и вызывает
`POST /api/pins/resolve` с заголовком гарда, а затем переводит браузер на страницу результата
(`/share?status=…`). Страница знает только параметры URL и показывает `Saved`,
`Already in the archive` или причину; если сервер не отвечает, worker показывает свою страницу вместо
ошибки Traefik.

Worker не склеивает поля в один URL: Pinterest кладёт ссылку то в `text`, то в `url`, а рядом —
заголовок пина, поэтому ссылку ищет сервер (`pinterest.first_link`) — слово за словом, отдавая
приоритет `pinterest.*`/`pin.it`. Короткая ссылка `pin.it` разворачивается отдельным запросом
(`pin.it` → `api.pinterest.com/url_shortener/…` → `/pin/<id>/`).

Страница результата всегда тёмная и не зависит от темы телефона: она открывается поверх чужого
приложения, и светлый вариант там терял контраст. Её `theme-color` задан явно тёмным (`#16171b`),
поэтому статусная строка тоже тёмная, со светлыми значками. То же значение стоит в манифесте
(`theme_color`); страницы со своим `theme-color` (главная и админка) его перекрывают.

Тот же резолвер доступен и с ПК: в шапке сайта есть поле и кнопка **Save link** — вставьте ссылку
(`pinterest.com/pin/…` или `pin.it/…`) и нажмите кнопку; текст вокруг ссылки не мешает.

iOS share-цель не поддерживает — там остаётся Save link на сайте.

## Веб-интерфейс

- сортировки **Newest / Oldest / Top / Random** и кнопка **Deleted** — показать только то, что
  удалено с Pinterest;
- счётчик под шапкой — сколько пинов загружено из общего числа;
- клик по картинке открывает полноэкранную карусель (`←`/`→`, `Esc`), на телефоне — свайп
  влево/вправо, щипок двумя пальцами увеличивает картинку (до 4×), увеличенную двигают одним
  пальцем, двойной тап возвращает исходный размер;
- кнопка `↗` на карточке открывает пин на Pinterest;
- кнопка `✕` на карточке удаляет пин из архива, с галочкой «Also delete the image file» — вместе
  с файлом в `originals/`.

## Проверка удалённых пинов

```bash
playwright install chromium   # один раз
python src/updateDelete.py
```

Скрипт открывает каждую ссылку в headless Chromium и ставит `is_deleted` тем пинам, которых больше
нет. Результат виден по кнопке **Deleted** в веб-интерфейсе.

## Бэкапы

```bash
python src/backup.py
```

В `backups/` появляется zip: база целиком плюс только те файлы из `originals/`, что новее прошлого
бэкапа. Время последнего бэкапа — в `backups/backup_state.json`. То же самое можно запустить кнопкой
со страницы обслуживания (см. ниже).

## Страница обслуживания

Сервер поднимает **второй порт** — страницу обслуживания: `http://127.0.0.1:8001`. Она отвечает
только на нём: на порту сайта её маршруты отдают `404`, потому что в ней нет авторизации, а она умеет
отдавать весь архив.

Что она умеет:

- **Полный бэкап** — ссылка, которая собирает zip на лету: согласованный снапшот базы (копия делается
  через online backup API SQLite, а не чтением файла, поэтому работающий сервер её не портит) и
  **все** картинки из `originals/`. На диск ничего не пишется: размер архива и свободное место не
  важны, скачивание начинается сразу;
- **Инкрементальный бэкап** — кнопка, которая делает ровно то же, что `python src/backup.py`: zip в
  `backups/` с базой и только теми картинками, что изменились с прошлого бэкапа;
- **Список бэкапов** — все zip из `backups/` с датой, размером и ссылкой на скачивание.

Параметры (`python src/server.py`; в Docker те же имена, значения по умолчанию — в `docker-compose.yml`):

| Переменная | По умолчанию | Что значит |
| --- | --- | --- |
| `PINSAVER_ADMIN_HOST` | `127.0.0.1` | адрес страницы обслуживания (в контейнере `0.0.0.0`) |
| `PINSAVER_ADMIN_PORT` | `8001` | её порт; `0` выключает её совсем, и он не должен совпадать с `PORT` |

В Docker она публикуется на `PINSAVER_ADMIN_BIND_ADDR` (по умолчанию `127.0.0.1` — только эта
машина). Если открыть её нужно и с других машин в VPN, поставь в `.env` адрес VPN-интерфейса
(`10.77.77.21`), но **никогда** не публикуй её в интернет.

Без браузера то же самое доступно так:

```bash
curl -OJ http://127.0.0.1:8001/api/admin/backup/full                            # полный архив
curl -X POST -H 'X-PinSaver-Request: 1' http://127.0.0.1:8001/api/admin/backup  # инкрементальный
```

## Импорт из экспорта Pinterest

Если база потеряна, а картинки в `originals/` остались:

```bash
python src/importer.py
```

Скрипт разбирает HTML-файлы экспорта Pinterest в корне проекта и восстанавливает записи по тем
картинкам, что есть на диске. Схлопнуть дубликаты по `file_id` можно так:

```bash
python src/migrate_duplicates.py
```

## Версия, хеш и релизы

Единственный источник версии — `__version__` в `src/buildinfo.py`; `tools/bump_version.py` переносит
её в `extension/manifest.json`, так что руками версию больше нигде править не нужно.

```bash
python tools/bump_version.py 1.2.0    # поднять версию в обоих файлах
python tools/bump_version.py --check  # проверить, что версии совпадают
```

- `GET /api/version` (`src/buildinfo.py`) отдаёт версию, коммит, дату коммита, признак незакоммиченных
  правок и ссылки на тег и коммит; сайт рисует из этого бейдж в шапке, расширение — бейдж в настройках;
- хеш у сайта и у расширения ведёт на коммит, версия — на `releases/tag/vX.Y.Z`; звёздочка у хеша
  означает, что в рабочей копии есть незакоммиченные правки;
- порядок релиза: `python tools/bump_version.py X.Y.Z` → коммит → `git tag -a vX.Y.Z -m "PinSaver X.Y.Z"`
  → `git push --follow-tags origin master` → GitHub Release по этому тегу.

Иконки расширения — тоже генерируемые: мастер-файл `extension/icon.svg`, из него рисуются PNG
(Chrome не умеет SVG-иконки):

```bash
python tools/make_extension_icons.py
```

Иконки PWA (`src/static/icons/*.png`) и `src/static/favicon.svg` рисуются из эмодзи шапки сайта
(📌) — так иконка на домашнем экране совпадает с шапкой, как в duosave:

```bash
python tools/make_pwa_icons.py
```

Манифест лежит в корне (`/manifest.webmanifest`), потому что Google при сборке WebAPK забирает его
и иконки **без сессии**: эти три пути открыты в sitehub и Cloudflare Access (см. «Публикация в
интернете»). Сам манифест отдаёт отдельный маршрут с типом `application/manifest+json`, а
`/favicon.ico` перенаправляет на `/static/favicon.svg`.

## Данные и безопасность

- Внутри приложения авторизации нет: единственный вход снаружи — Cloudflare Access (см. «Публикация в
  интернете»). Локально сервер слушает `0.0.0.0` — держи его в доверенной сети.
- Изменяющие запросы (`POST /api/pins`, `POST /api/pins/check`, `DELETE /api/pins/{pin_id}`) требуют
  заголовок `X-PinSaver-Request: 1` и отвергают чужие `http(s)`-источники: страница со стороны не может
  ни добавить, ни удалить пин. Расширение и service worker ставят заголовок сами.
- `GET /images/{filename}` принимает только простое имя файла: до 2.0.0 `..%5c..` позволял прочитать
  любой файл на машине, включая `.env` и саму базу — теперь это закрыто и покрыто тестом.
- `/share` в базу не пишет вообще: страница результата собирается из параметров URL, а сохранение
  идёт только через `POST /api/pins/resolve` под гардом. Service worker не кеширует ничего, поэтому
  устаревшая страница или чужой ответ в кеше появиться не могут.
- У контейнера нет доступа к `docker.sock`, git и хосту: обновление запускается вручную с хоста
  (`deploy\windows\update.ps1`).
- Из браузера к API обращается только расширение: CORS открыт исключительно для `*.pinterest.com`
  (и только чтобы обойти Private Network Access), остальные источники получают отказ.
- Страница обслуживания живёт на отдельном порту и отвечает только там: её маршруты сверяют порт
  сокета, принявшего запрос (`scope["server"]`), а не заголовки, поэтому подделанный `Host` или
  `X-Forwarded-*` её не открывает, а на порту сайта они отдают `404`. Авторизации в ней нет, поэтому
  порт публикуется только на локальных адресах и никогда — в интернет.
- `POST /api/admin/backup` — изменяющий запрос: он требует тот же заголовок `X-PinSaver-Request: 1`,
  а второй одновременный бэкап получает `409`.
- `pinterest_archive.db`, `originals/`, `backups/`, `testPages/` и `.env` перечислены в `.gitignore` —
  в репозиторий попадает только код.
- Перед рискованными операциями делай `python src/backup.py`.
